## 16. Acceptance criteria

Parley is accepted when the following hold, demonstrated by black-box tests against a running hub using only the REST API, the `parley` CLI and stock `git`.

1. **Change as the unit of work (§7).** A pushed branch becomes a change with a stable number. Each of five successive pushes, including a force push, yields a new version; all five heads are fetchable by version ref. The interdiff between a version and its pure rebase is empty. A commit landed on a protected branch resolves to its change, version and session; a commit that arrived by a direct push of the owner resolves to no change (`change: null`) and to its `parley.git.push` event with `direct: true`.
2. **Stacks (§7).** Three stacked changes are opened by pushing three branches. Amending the bottom one produces `restack` versions of the two above without client action. Landing the bottom one rebases the next onto the target and clears its `depends_on`. A restack that cannot apply sets `needs_restack` with a conflict report and moves nothing.
3. **Task forks (§4).** One call returns a fork, its remote and a token. The fork is usable at once for a repository of at least 1 GB, and creation time does not grow with repository size. The token is refused everywhere outside the fork except for its own changes and the parent's awareness and policy reads (§3). A push to a tracking branch is refused. A fork created without `ttl` expires 7 days after creation. The fork disappears at its TTL, and earlier, 24 hours after all its changes have landed or been abandoned.
4. **Source control API (§6).** Without any clone: read a file, a tree, a path's history, a diff and blame; create a commit of several files; observe `409 ref_moved` on a stale `expected_head_sha`; open and land a change. The resulting repository is identical to one produced by the equivalent git operations.
5. **Optimistic landing (§8).** Twenty changes touching twenty different files are landed concurrently on one target: all land, none of the callers retries, the history is linear and contains each change once. Two changes editing the same lines are landed concurrently: exactly one lands, the other ends `conflict` with a report naming the file and the landed change, and the target contains only the first. A hub killed during a land restarts into a state where the change is either fully landed with its event, or not landed at all.
6. **Conflict resolution without a clone (§8).** The conflicted file is fetched with markers, a resolution is submitted, and the change then lands.
7. **Policy by path (§8).** With a policy of three rules (automatic, check required, approval required, plus one blocked path): a docs-only change lands with no approval; a change needing a check is `pending` until the check is reported `passed`; a change needing approval does not count the approval given with the credential that pushed it, and counts one from another credential; a change touching the blocked path cannot land, even with an override. An approval survives a pure rebase and does not survive a content change. `evaluate` predicts each of these before the change exists.
8. **Path-scoped tokens (§3, §5, §6).** A token limited to `a/**` can push and commit changes under `a/` and is refused, with the offending path named, for a commit touching `b/x`, over git and over the API alike.
9. **Protected branches (§5, §6, §8).** A protected branch moves by landing, by sync from origin, and by a direct fast-forward push from the workspace's owner or the admin token. With the owner's API key, a fast-forward git push, an API commit and a fast-forward API ref move of a protected branch each succeed and emit `parley.git.push` with `direct: true`. The same operations are refused with a workspace-bound token of the owner, with a path-scoped token of the owner and for an org member. A forced update and a delete are refused with every credential, including the admin token. With `protect.owner_push` set to `false`, every direct update is refused for every credential.
10. **Automatic landing and revert (§8).** A change with `auto_land` lands by itself once its required check passes. A landed change is reverted by one call, and landing the reverting change restores the previous content.
11. **Awareness (§9).** With two open changes touching the same file, each receives one `parley.change.overlap` event naming the other. `activity` for that path returns both changes and a live claim, and no longer returns the claim after it expires. No awareness state ever causes a push or land to be refused.
12. **Durable events (§14).** A consumer that disconnects, misses fifty events and reconnects with its last `seq` receives exactly those fifty, in order, then live events. A cursor older than retention gets `410 cursor_expired`. Events for a push, a fork, a version, a land and a conflict each carry the session given on the operation. No event is missing after the hub is killed and restarted under load. An event webhook subscribed to the workspace receives the same events as signed `POST`s in `seq` order: the receiver verifies `Parley-Signature` with the secret shown at creation; while the receiver answers `500`, the hub retries the same delivery id with backoff and sends no later event; when the receiver answers `2xx` again, the held events arrive in order, none missing. A subscription whose URL resolves to a private address is refused. A ping and a redelivery each arrive signed.
13. **Sessions as the thread (§14).** From a session id, the fork, the changes, their versions and their land attempts are reachable. From a landed commit, the session is reachable.
14. **Git compatibility (§5).** Stock `git` clones (full, shallow, and with `--filter=blob:none`), fetches and pushes through the hub with a PAT and the credential helper. A workspace the caller cannot read is indistinguishable from one that does not exist.
15. **Carried features.** Workspaces (§4), carry-patch workspaces (§10), secrets and variables (§11), forge integration (§12) and sessions, audit and metrics (§14) each pass a test of every listed success and error case of their REST routes and CLI commands.
16. **Conventions (§3).** Every error on every route is the envelope with an `error_type`. Every list is paged the same way. Every creating `POST` honours `Idempotency-Key`. A wrong method is `405`.
17. **Operations (§15).** The hub runs from one binary, one configuration file and one data directory. A backup taken while running restores to a hub that starts cleanly. The performance targets of §15.4 are met on the reference host.
18. **Sandboxes (§13).** Demonstrated against a hub connected to an OpenShell gateway. One fork-create call with a `sandbox` object returns a fork and a sandbox; when the sandbox is `ready` the fork is checked out in it, and a `git push` run inside it opens a change in the parent. A command run in the sandbox cannot read the value of the hub credential or of an attached credential: it sees placeholders only. With a profile that lists nothing in `expose_secrets`, no secret value is in the sandbox's environment. With a profile that lists a secret there, a command in the sandbox reads its real value from the environment; the profile list, the sandbox object and `parley.sandbox.create` name it and never show the value; the value is `[redacted]` in the stored sandbox log; and a missing required one refuses the creation with `422 credential_missing`. A fork owned by a read-only org member does not get a parent's secret exposed. A request from the sandbox to a host that no rule allows is blocked and reported as `parley.sandbox.deny`. A proposal for that host cannot be approved with a workspace-bound token (`403 token_bound`); once a person approves it, the same request succeeds. Approved with `scope: workspace`, the rule is listed under the workspace's sandbox rules, a sandbox created afterwards on the workspace or on another of its forks reaches that host without a proposal, a sandbox that was already running does not, and after the rule is deleted a newly created sandbox is blocked again. A fifty-first running sandbox on one workspace family is refused with `429 sandbox_capacity` naming `max_per_workspace`, and the hub, organization and user limits are each named the same way when they are the one hit. A requested stop, an idle stop and expiry each leave a checkpoint under `refs/parley/sandboxes/`, and a new sandbox created with `restore_from` has the committed and the uncommitted work back. A hub restart leaves a running sandbox and its main process untouched, and the hub shows it `ready` again afterwards. A token that lacks a scope of the sandbox's hub credential cannot exec in it (`403 insufficient_scope`). Every listed success and error case of the sandbox routes and commands passes its test.
